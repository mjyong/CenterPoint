# kygi665 机器狗的传感器

这份文档汇总机器人上和感知有关的传感器：型号与官方参数、在机器人上的安装和外参、ROS 话题与消息格式、时间戳，以及实测时发现的问题。

代码里对应的常量：
- 雷达预设：`dog_perception/lidars.py`
- INS、IMU：`dog_perception/inspvax.py`
- 在线节点参数：`dog_perception/node_config.py`

各工具怎么读这些数据，见 [DATA_LINEAGE.md](DATA_LINEAGE.md)；bag 的切分和检查，见 [BAG_SPLIT.md](BAG_SPLIT.md)。

## 1. 坐标系和外参

### 1.1 坐标系

| 名称 | 原点 | 轴 | 说明 |
|---|---|---|---|
| L：XT32 雷达系 | 雷达原点 | x 左、y 后、z 上（z 为旋转轴） | 驱动发布的点云坐标 |
| I：IMU 系 | IMU 中心 | x 右、y 前、z 上 | 组合导航的轴；天线杠杆臂也在这个系下给出 |
| base：机器人本体系 | 机器人本体原点 | x 前、y 左、z 上 | 机器人标定用的系（`imu2body`） |
| B：代码里的机身系 | **XT32 雷达原点** | 同 I（x 右、y 前、z 上） | 所以外参只有旋转（绕 z 转 180°），`base_height` 就是雷达离地高度 |
| W：世界系 | 第一个可用 INS 解的位置 | 东、北、天（ENU） | |
| D：检测系 | 雷达正下方的地面 | 航向随机身，重力对齐 | 加 `auto_ground` / `auto_level` 在线修正离地高度和倾斜 |
| M：网络系 | | D 绕 z 转 +90°，z 减 1.84 m | 虚拟的 nuScenes 雷达系，让预训练模型的高度先验成立 |

- 第 n 线（从上往下数）的设计俯仰角是 16 − n 度：第 1 线 +15°，第 16 线 0°，第 32 线 −16°。各线水平角偏移都是 0°，准确值在每台雷达自己的角度校正文件里。

## 3. 组合导航（GNSS 双天线 + IMU）

### 3.1 INSPVAX `/rte/rdap/rtk/inspvax`

格式和 NovAtel INSPVAX 相同，100 Hz。用到的字段：

| 字段 | 用法 |
|---|---|
| `ins_status` | 3 = `INS_SOLUTION_GOOD` 才用；第一个好解作为 ENU 原点 |
| `pos_type` | 56 = RTK 固定解（实测位置标准差约 1.3 cm）。`kygi665_msgs` 里的常量名把 55 / 56 写反了，按 NovAtel 标准以 56 为固定解 |
| `latitude` `longitude` `height` | 换成 ENU，再按杠杆臂挪到机身原点 |
| `north/east/up_velocity` | 速度 |
| `azimuth` | 航向，北向顺时针；机身航向 `yaw = 偏置 − azimuth`（ENU，东向逆时针） |
| `roll` `pitch` | **不用**：0921 急停时 pitch 在 0.6 s 内从 +2.8° 摆到 −9.9°，而陀螺积分不到 2°（主要是天线接反造成的，见下）。倾斜由点云在线找平 |

### 3.2 双天线和"接反"

- 两个 GNSS 天线沿机身前后方向安装（1.2 节）。航向由两天线连线的方向给出，基线 0.6546 m。实测航向标准差约 0.2°。
- **0921 录制时主、从天线接反了**：INS 的方位角指向机器人后方（偏 179.5°），所以转换时偏置取 180°。这还带来了几个后果：
  - INS 把水平加速度投影到了反方向：急停时速度冲到 2.5 m/s，位置超前约 0.45 m；
  - 快速转弯后航向偏 4–10°；
  - 刹车时 pitch 乱摆。

  这些都由 `refine_poses.py`（激光里程计 + RTK 融合）修正。
- **INS 输出位置在哪里**：INS 的输出点设在 IMU 中心（机器人团队 2026-10-22 确认），B 系下 (0.021, −0.180) m（`KYGI_IMU_IN_BODY`）。天线接对后，代码默认就按这个点算。

  接反时，INS 用配置的主天线杠杆臂、但航向转了 180° 去倒推 IMU 位置。算出来的点落在 IMU 后方 0.474 − 0.180 = 0.294 m 处（两天线杠杆臂之和），B 系下是 **(0.021, −0.474) m**（`dog_perception/inspvax.py` 的 `ins_point_with_swapped_antennas()`）。

  用 0921 的 14 个转弯场景拟合出的是 (−0.06, −0.54) m（`KYGI_INS_LEVER_ARM`）。两者相差 0.10 m，方向一致，解释了之前"INS 点在雷达后方约 0.54 m、不在 IMU 中心"的现象。拟合值本身的留一法波动在 3 cm 以内，所以剩下的约 0.1 m 还没完全解释，现在仍用拟合值。
- **1016 录制天线已经接对**：方位角和行进方向只差约 9°，转换器自动选偏置 0。以后的录制默认如此；转换器和在线节点都会检查（机器人沿 B 系 +y 前进），不对会告警。

### 3.3 IMU `/rte/rdap/rtk/imus/data_raw`

### 4.2 在机器人上（1016 录制实测）

- 三个话题都是 `foxglove_msgs/CompressedVideo`，`format` = h264（Baseline profile，level 5.0），1920 × 1536，**24 Hz**。
- 关键帧大约每 30 帧（1.25 s）一个，每条消息都带 SPS。每路每帧 7–20 KB，三路合计约 1.2 MB/s（约 4.3 GB/小时），是 XT32 数据量的 4%。
- `timestamp` 比写入 bag 的时间早约 1 ms。
- **三路的 `frame_id` 都是 `camera`**，建议改成 `front_camera` / `left_camera` / `right_camera` / `rear_camera`，否则以后标定后无法区分。
- 机器人上共 **4 个**鱼眼（前、后、左、右），只录前、左、右三路，后视不录。
- 安装位置见 1.2、1.3 节。从画面看：
  - 前视在机头，朝前略向下，画面下沿能看到机身前部的把手；
  - 左、右在机身两侧，朝两侧，画面下方两角能看到腿。
- 内参见 4.4 节。相机朝向还没有标定。代码（`dog_perception/cameras.py`）已经有投影模型和安装位置，朝向标定后就能把点云和 3D 框画到画面上。
- 粗略验证：按等距鱼眼模型（f ≈ 460–500 像素）把点云投到前视图上，行人、栏杆、车头大致对得上。要画框到图上，需要正式标定。

### 4.3 要录几路？

**录前、左、右三路**（后视不录），审核以前视为主，左、右用来确认侧面的车。

- XT32 是 360° 的，标注覆盖机器人周围 ±40.8 m 的全部范围。前视鱼眼只看得到前方 ±98°，后方 164° 的扇区看不到。
- 0921 的自动标注里，车辆框按方位分布：

  | | 前视 ±98° 以内 | 前视看不到（后方） | 两侧 60–120° |
  |---|---|---|---|
  | 全部车辆框（35,533 个） | 70% | 30% | 38% |
  | 20 m 以内 | 64% | **36%** | 46% |

  只用前视的话，约三分之一的车（近处更多）没有画面可以对照，正好是审核最难判断的那部分：侧面停着的车、从后面过来的车。
- 每个鱼眼 196°，两侧正是车最多的方向（上表 38%，20 m 内 46%），左、右相机正对着它们。
- 正后方（|方位| > 120°，占车辆框的 16%）只能在左、右相机的边缘看到，像小、畸变大。这部分车审核时主要看点云。
- 腿和机身会挡住各相机画面下方的一部分。
- 代价很小：每路 H.264 约 0.4 MB/s，三路约 1.2 MB/s，约为 XT32 数据量的 4%。实在要省，可以把帧率降到 10–12 Hz，审核够用。
- 审核时在 Foxglove 里放三个 Image 面板（`review_labels.py mcap --cameras`），配合点云的 3D 面板看。

### 4.4 内参

机器人团队提供了一台相机的出厂标定，**暂时四个相机都用这一套**。每台相机的镜头装配略有差异，所以不会很准，以后最好每台一套。

## 6. 输出点和时间同步：要确认的三件事

所有话题都用消息头的时间（`header.stamp` / `timestamp`），不用写入 bag 的时间。下面三件事决定这些时间和位置能不能直接对上。

### 6.1 INS 的输出点

**结论**：输出点设在 IMU 中心（机器人团队 2026-10-22 确认），和代码的默认值一致，不用改。下面是原来的说明。

**是什么**：组合导航报的经纬度，是机器人身上某一个点的位置。这个点可以是：
- GNSS 天线；
- IMU 中心；
- 在 INS 配置里用"输出偏移"（NovAtel 叫 user offset / output translation）设的任意一点。

**用来做什么**：我们需要的是雷达（B 系原点）的位置。代码用"输出点 → 雷达"的杠杆臂把 INS 位置挪过去：天线接对时按输出点在 IMU 中心算（0.18 m）。

**设错了会怎样**：机器人直行时看不出来；一转弯，算出来的雷达位置就会在一个以杠杆臂为半径的圆上多走一段。
- 例如杠杆臂错 0.18 m，原地掉头会多出 0.36 m 的位移；
- 以 90°/s 转弯时，多出约 0.28 m/s 的假速度。

结果是多帧叠加时静止物体拖出重影，自动标注会把停着的车标成在动。

**怎么确认**：
- 在 INS 的配置（上位机或配置命令）里看输出点 / 输出偏移是怎么设的；
- 用数据确认：`refine_poses.py` 会打印残余杠杆臂（`lever_residual_m`），接近 0 就说明假设对了。

0921 接反时按"输出点在 IMU 中心"推算的点，和拟合值差 0.1 m（3.2 节）。既然输出点确认在 IMU 中心，这 0.1 m 不是配置造成的，可能来自拟合本身（激光里程计的误差）或天线相位中心的位置。用 8.3 节第一项在服务器上比一下就清楚了。

### 6.2 雷达授时：GPS 还是 PTP

**是什么**：雷达给每个点打时间戳用的是自己内部的时钟。要和 INS、IMU 的时间对得上，这个时钟得从同一个时间源校准，叫授时。XT32 支持两种：

| | GPS 授时 | PTP 授时 |
|---|---|---|
| 怎么接 | GNSS 接收机（一般就是这台组合导航）额外引两根线到雷达：PPS 秒脉冲（硬件信号，标出每个整秒的时刻）+ 串口 NMEA（$GPRMC / $GPGGA，告诉雷达现在是几点几秒） | 走以太网：网络里要有一个 PTP 主时钟（例如本体的计算机或交换机，自己再对准 GNSS），雷达作为从时钟自动对时 |
| 精度 | 约 1 μs | ≤ 1 μs（手册） |
| 需要什么 | 两根线；雷达设置里选 GPS，确认 PPS 和 NMEA 都"锁定" | 一个 PTP 主时钟（支持硬件时间戳的网卡 / 交换机）；雷达设置里选 PTP |
| 掉线时 | 失锁后按内部时钟走，慢慢漂移 | 主时钟断了按内部时钟走，漂移 ≤ 1 μs/s |
| 从没锁上时 | 从虚拟时间 2000-01-01 00:00:00 开始计时 | 同左 |

两种方式精度一样，区别只在接线和依赖的设备。对我们来说，**用哪种都行，要确认的是"锁上了"，而且和 INS 是同一个时间源。**

**用来做什么**：
- 去畸变：一圈扫描 0.1 s，机器人在这 0.1 s 里的运动要按每个点自己的时间去补；
- 多帧叠加：网络输入是 5 帧拼起来的，要用每帧时刻的位姿把旧帧挪到当前帧。

**有偏差会怎样**：雷达和 INS 差 δ 秒，就等于用错了 δ 秒前（后）的位姿。
- 以 90°/s 转弯、δ = 20 ms：角度错 1.8°，10 m 外错 0.3 m；
- 以 2 m/s 直行、δ = 20 ms：错 4 cm。

转弯时问题最明显：墙变厚、车拖重影。如果时钟从没锁上，雷达时间从 2000 年算起，和 INS 差二十多年，转换器会直接对不上。另外，有的驱动在雷达没锁时改用电脑收到数据的时间，那样会有几毫秒到几十毫秒的延迟和抖动。

**我们现在的情况**：0921 上用转弯检查（`time_offset_check.py`）和"IMU 陀螺 z 与 INS 航向变化率"的相关性（0 延迟处最高，0.91）验证过，没有可见的时间差，说明当时是对上的。

确认授时方式，是为了知道以后每次上电要检查什么：
- GPS 授时：查 PPS / NMEA 锁定状态；
- PTP 授时：查 PTP 状态是 tracking / locked。

**顺带一个可选功能**：XT32 支持相位锁定（Sync Angle）：每个整秒转到指定的方位角。配合相机硬件触发，可以让雷达扫过某个相机视场的时刻正好是这个相机曝光的时刻，做相机-雷达融合时最准。只做审核不需要。

### 6.3 相机：是不是硬件触发

**是什么**：
- **自由运行**：相机按自己的节奏拍（例如 24 / 30 fps），什么时候曝光由相机内部时钟决定，四个相机之间、和雷达之间都不同步。消息里的时间戳通常是图像到达电脑（或编码完成）的时刻，比真正曝光晚一段：采集卡、ISP、H.264 编码，一般几十毫秒，还会抖动。
- **硬件触发**：由一个外部信号（例如采集卡按 PPS 对齐后产生的触发脉冲）控制什么时候曝光。四个相机同时曝光，时间戳就是曝光时刻，和雷达、INS 在同一个时间轴上。H190XA 支持外部触发和多相机同步（帧同步由串行器 MAX96717F 的 MFP7 控制）。

**用来做什么**：只看画面对照（审核时人眼看车在不在），不需要同步，差几十毫秒没关系。要把点云或 3D 框**画到图上**，或者做相机-雷达融合、外参自动标定，就需要知道每帧的准确曝光时刻。

**有偏差会怎样**：差 Δt 时，画上去的框会偏。
- 机器人以 90°/s 转弯、Δt = 50 ms：画面转了 4.5°，鱼眼上约偏 40 像素；
- 一辆 10 m/s 开过的车，Δt = 50 ms：车本身挪了 0.5 m。

**我们现在的情况**：1016 里相机时间戳只比写进 bag 的时刻早约 1 ms，看起来是"到达电脑的时间"，不是曝光时间。真正的延迟不知道。没有硬件触发也能用：拿到内参和外参后，可以用一段有车开过的数据，比较投影的框和画面里的车，把固定延迟估出来补上。
